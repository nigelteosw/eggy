# Database choice and PostgreSQL migration — draft plan

Status: proposed for owner review; no implementation or deployment authorized by this document.

## Goal and recommendation

Let an operator choose SQLite or PostgreSQL, understand the operational tradeoff, set up the selected database, inspect and apply schema migrations, and move an existing SQLite home to PostgreSQL without losing private state.

Recommend keeping SQLite as the default and adding PostgreSQL as an alternative adapter. Exactly one database is authoritative per deployment. YAML remains startup configuration and Markdown remains owner-facing memory; PostgreSQL replaces SQLite's machine-managed role when selected. PostgreSQL does not replace USER.md, MEMORY.md, skills, logs, or the persistent home volume.

This is an explicit exception to AGENTS.md's SQLite-only durable-form rule and prohibition on adding a database. Approval of this design should authorize updating those rules to “one selected relational database, SQLite or PostgreSQL.” It does not authorize a pluggable memory system, another daemon loop, or multiple Eggy replicas.

Alternatives considered:

| Approach | Benefit | Cost / recommendation |
| --- | --- | --- |
| SQLite default, PostgreSQL option | Existing homes keep working; operators can choose managed infrastructure | Two SQL implementations and integration coverage; recommended for the requested choice |
| PostgreSQL only | One SQL implementation after migration tooling retires | Mandatory external service for every owner; choose this if removing SQLite is more important than database choice |
| SQLite state plus PostgreSQL search | Smaller initial persistence change | Two authorities, synchronization and recovery complexity; reject |

## Capabilities: what the choice buys

- PostgreSQL has built-in full-text search. Eggy already uses SQLite FTS5 in `plugins/store/sqlite/store.go`; this migration replaces that implementation, rather than introducing search for the first time. See [PostgreSQL text search](https://www.postgresql.org/docs/17/textsearch-intro.html).
- [pgvector](https://github.com/pgvector/pgvector) adds vector storage and similarity indexes. Installing it does not create embeddings or choose an embedding model. Semantic retrieval needs a separate product design covering sources, account isolation, embedding costs, model/dimension changes, and deletion.
- [Apache AGE](https://age.apache.org/overview/) adds graph functionality as an extension. Provider support and PostgreSQL-version compatibility must be checked before adopting it. Graph extraction and traversal are separate features, not prerequisites for moving persistence.
- PostgreSQL is not a bundled Redis server. For example, [redis_fdw](https://github.com/pg-redis-fdw/redis_fdw) connects to an external Redis database. Use relational tables for existing durable state; do not add Redis, a Redis protocol layer, or a cache solely because integration exists.

First delivery uses standard PostgreSQL with no required extensions. Show optional capability availability as information, without installing extensions or starting embedding work. Search, graph, and vector enhancements can then be reviewed independently.

## Operator experience

### Choose and connect

Add a Database section to the existing authenticated administration surface:

1. Choose **SQLite — local, no server to manage** or **PostgreSQL — connect to a database you manage**.
2. SQLite shows its resolved home path. PostgreSQL asks for the environment-variable name containing the connection URL, defaulting to `EGGY_DATABASE_URL`; the UI never reads back the URL or password.
3. Offer two documented setup paths: managed PostgreSQL, or a supplied optional Docker Compose service for self-hosting. The operator provisions the database/user; Eggy does not receive a cloud account credential or Docker socket.
4. **Test connection** checks connectivity, TLS, server compatibility, schema version, and required privileges using bounded requests. It must not create tables or migrate. Render actionable, credential-free errors.
5. Show **Ready**, **Migrations pending**, **Connection unavailable**, or **Database newer than this Eggy**. Include active versus configured backend, redacted destination identity, applied version and pending migration names.
6. A fresh home can choose **Initialize and use PostgreSQL** after reviewing the migration list. An existing home sees **Move existing data**, with the offline command sequence below; saving a selector alone must not activate an empty destination.

Proposed minimal configuration:

```yaml
database:
  provider: postgres # sqlite is the default when omitted
  url_env: EGGY_DATABASE_URL # only meaningful for postgres
```

Keep SQLite's existing `<home>/eggy.db` path. Resolve secrets through `internal/config`, add the resolved URL to `Secrets.Values()`, and sanitize driver errors independently: a driver may print only a password or URL fragment. Do not log connection strings or expose credentials in tool output, UI, migration reports, or prompts. Connection URLs can carry pool/TLS options supported by the chosen driver; explicitly bound connection establishment and operations in code. Require verified TLS for remote connections; document explicit local-container TLS configuration.

Database selection affects the whole deployment. In account mode only the existing administrative principal may configure it or run checks; ordinary accounts must not gain global configuration authority. Reuse authentication and CSRF protection. This is operator administration, not an agent tool.

### Headless setup and recovery

Add these proposed operator commands to the existing `eggyd` binary, dispatched before normal daemon startup:

```text
eggyd db status
eggyd db check
eggyd db migrate --plan
eggyd db migrate --apply
eggyd db import-sqlite --source /data/eggy.db --target-env EGGY_DATABASE_URL --check
eggyd db import-sqlite --source /data/eggy.db --target-env EGGY_DATABASE_URL --apply
```

`status`, `check`, and `--plan` are read-only and must not call today's schema-mutating SQLite `Open`. `migrate --apply` requires exclusive maintenance access and prints the exact migrations before confirmation; scripted operation uses an explicit confirmation flag. UI and CLI invoke the same maintenance implementation supplied by bootstrap, not separate SQL code paths.

The web surface displays migration status and the exact host commands for an existing deployment. Apply offline while Eggy is stopped; this avoids a background migration job, a second execution loop, and interrupting authenticated requests midway through a schema change. Fresh-database initialization follows the same migration runner before normal startup. Routine startup validates compatibility; it does not silently perform pending upgrades. The release introducing this policy must document the new operator step for existing SQLite homes.

If PostgreSQL is unavailable, never fall back to SQLite. Account-mode safe-mode login itself needs the selected session database; fail closed and show host-side recovery instructions when it cannot authenticate. Do not add a fallback owner password or an unauthenticated database setup route. First-run setup and database-outage recovery therefore work through the CLI and deployment environment even without the web panel.

## Architecture and semantics

Add `plugins/store/postgres/` using a small Go PostgreSQL driver such as pgx through `database/sql`; confirm the pinned release and Go compatibility at implementation. Use explicit SQL, no ORM or general SQL-dialect framework. Reuse existing service-facing interfaces unchanged. Replace SQLite concrete types in bootstrap with the narrow interfaces their consumers already require, including session, identity, grants, schedules and home-migration markers. Do not introduce a generic module lifecycle or export SQLite internals just for the new adapter.

Bootstrap alone chooses and wires the active adapter. Maintenance command dispatch delegates to bootstrap construction; migration SQL and connection behavior stay with each adapter. Any shared maintenance orchestration must be a small concrete workflow justified by the UI and CLI callers, not a provider registry framework.

Port behavior, not just table definitions:

- Preserve account predicates on reads, updates, searches, deduplication and deletes, including traces and thread workspaces.
- PostgreSQL concurrency cannot rely on SQLite's one connection. Use transactions, row locks and conditional updates for state/grant read-modify-write, schedule claiming and one-time login consumption. Concurrent first inserts need conflict handling as well as locks on existing rows.
- Keep approval IDs, payloads, account binding and modes unchanged. Import does not authorize execution or reset approval mode.
- Preserve timestamps without truncating nanoseconds and preserve schedule timezone/offset meaning. Initially retain integer and RFC3339Nano encodings where precision or offset matters; do not blindly convert all fields to `timestamptz`.
- Keep sealed grant bytes and associated-data identifiers intact. The existing encryption key stays in the home/environment, never in the database.
- Translate placeholders, generated IDs, conflict clauses, booleans and result semantics explicitly. Reseed generated identifiers after import.
- Implement `SearchText` with a stored/generated `tsvector` and GIN index, a defined text configuration, literal user-query handling, bounded results and account filtering before limiting. Document tokenizer/ranking differences from FTS5; test behavior rather than identical ranking scores.
- Close the selected pool on startup errors, restart and shutdown. Selecting SQLite creates no PostgreSQL connection, pool, probe or goroutine.

## Schema migration contract

Use ordered, embedded SQL migrations per adapter, with a database-local ledger recording version, name, checksum and applied time. Retain the existing machine-state compatibility stamp: physical migration ordering and compatibility refusal serve different purposes and must be named separately. Add an explicit version bump if SQLite durable shape changes; preserve historical imports and the version-7 account upgrade.

Check version compatibility before any schema write, including base `CREATE TABLE` statements. Refuse a newer version and a changed checksum for an applied migration. Baseline existing SQLite homes only after validating the expected schema, not by stamping an arbitrary database current.

Use a PostgreSQL advisory lock on a dedicated connection for the entire migration, and SQLite's exclusive maintenance locking for its runner. The daemon and offline commands must share an ownership protocol so maintenance cannot race an active process. A second daemon must also fail to acquire ownership: PostgreSQL support does not authorize two replicas. Account for direct connections versus transaction-pooling proxies; session-level ownership locks require a dedicated direct/session-pinned connection.

For the initial scope, require transactional migrations and update the ledger in the same transaction. A failed migration rolls back and remains pending. Do not add automatic down migrations. Future nontransactional operations such as concurrent index builds require an explicit recovery design before being accepted. Existing deployments take a verified backup before applying changes; rollback restores a matching binary, configuration, home and database snapshot.

## Moving an existing SQLite home

Treat data transfer separately from schema upgrades:

1. Run read-only checks: source schema support, complete ownership/document migration, target reachability/version, empty dedicated target, and access to the existing sealing key. Refuse legacy/incomplete sources with precise upgrade instructions.
2. Stop Eggy, acquire exclusive maintenance ownership, and take a consistent SQLite backup plus home/config/key backup. Include WAL safely using a database backup mechanism or a cleanly closed database; copying a live main file alone is insufficient.
3. Initialize the target schema through the same migration runner. Import all authoritative tables in one transaction with explicit mappings. Include messages, threads, resets, traces/spans, machine state, approvals, processed events, proactive records, schedules, auth records, identities, sessions, login transactions, and import/account/document markers. Rebuild search indexes rather than copying FTS internals.
4. Verify counts by table/account, canonical row digests, identifiers, timestamp precision, schedule fields, ownership and representative grant decryption without displaying plaintext. Check every source table is either mapped or explicitly classified as a derived index; an unknown table fails the transfer.
5. Record transfer completion and a source fingerprint in the destination transaction. On failure roll back imported rows; an interrupted attempt may retry against the initialized but empty target. An already completed matching transfer reports success without duplication; a nonempty unrelated target is refused.
6. After verification, write the database selector through `internal/config`'s lock and atomic mutation. A crash between destination commit and config write is recoverable from the completion marker. Require the stopped source still matches its fingerprint before completing cutover.
7. Start Eggy on PostgreSQL and verify login, private history, search, approval state and schedule execution. The source SQLite file remains untouched as the pre-cutover recovery copy. Retain Markdown and sealing keys in the same home.

Before the first PostgreSQL write, rollback can restore the prior config and SQLite snapshot. Once PostgreSQL has accepted writes, switching back to the old SQLite file loses those writes and can replay old scheduled/approval state. Stop and restore a coordinated backup only with an explicit loss window; PostgreSQL-to-SQLite reverse transfer is outside the first delivery. Make this limitation visible in the cutover instructions.

## Footprint / deletion budget

This is a feature with unavoidable positive production-line growth, not a line-count cleanup. Retaining choice retains both adapter implementations. Record actual additions/deletions per phase; do not claim a net reduction without evidence.

- Production deletions: hardcoded SQLite selection in normal/recovery wiring; superseded schema-init paths when the migration runner owns them. Keep required historical migration code.
- Configuration: two keys (`database.provider`, `database.url_env`), one resolved secret; no per-capability toggles in the core migration.
- Agent tools: zero. Background application loops: zero. Eggy replicas: one. Selected runtime database/pool: one.
- Durable records: schema-migration ledger and transfer completion metadata in the selected database; no fourth file format or cache authority.
- External infrastructure: one PostgreSQL service only when selected, managed externally; no Redis or graph service.
- Optional vector/graph features: no production code, embeddings, tables or indexes until separately approved.

## Review choices

Recommended defaults for review: retain SQLite as default; standard PostgreSQL with no required extensions; explicit offline schema upgrades and data cutover; web selection/status with host commands for existing-home maintenance; no reverse transfer in the first release. If the intended outcome is PostgreSQL-only, revise the adapter-retention and SQLite retirement phases before implementation.
