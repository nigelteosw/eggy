# Spaces Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Use superpowers:subagent-driven-development only if the user explicitly chooses delegated execution. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give Eggy isolated personal and shared Spaces, with guest participation in approved Telegram groups, owner-only private access and administration, configurable action permissions, shared memory, and enforceable usage quotas.

**Architecture:** Extend the existing turn service, context adapter, SQLite stores, and approval gate with a verified Space scope. Keep owner authentication distinct from shared execution. Bootstrap remains the composition root; channel adapters normalise verified events, and `internal/config` remains the policy mutation authority.

**Tech Stack:** Go 1.26, standard-library HTTP, existing SQLite/Markdown/YAML adapters, React/TypeScript/Vite and Bun tests. No new runtime framework, database, agent loop, or scheduler.

**Spec:** [Spaces design](../specs/2026-09-16-spaces-design.md).

## Global constraints

- One Telegram group or Discord channel maps to one shared Space. No cross-group sharing or bridging.
- Only existing Eggy owners may administer Spaces or access internals. Platform group administrators gain no Eggy privileges.
- Only directed messages are retained and used. A directed reply may include its single referenced message, never a surrounding-history fetch.
- One permission policy applies to everyone in a Space, including owners. Resource ownership checks can restrict an action to the speaker's own resource.
- Personal `/mode strict|normal|auto` retains its existing semantics. Shared Spaces use their action map instead, within the same gate.
- YAML remains the policy/config authority, Markdown remains owner-facing context, SQLite remains machine-managed state.
- New capabilities are denied until explicitly enabled. Read-only classification alone does not establish group eligibility.
- No guest-facing web UI. No guest accounts. No personal Principal on shared execution contexts.
- No production code, commit, deployment, bot installation, or external configuration is authorized by writing this plan.

## Delivery boundary and execution order

Personal Discord DMs ship first under the independent [personal Discord plan](2026-09-16-spaces-discord.md). This foundation and both platforms' group support are deferred. When group work begins, Tasks 1–10 deliver the foundation with Telegram groups; the [Discord shared-channel plan](2026-09-17-discord-shared-channels.md) consumes these contracts and extends the existing Discord adapter. Owner DMs do not depend on completing this foundation. D&D tools and image generation are outside both plans. Image quota support is exercised with a fake paid capability until an image adapter exists.

Run tasks in order. Do not expose shared ingress before scope, persistence, permissions, quota, and approval checks are integrated. Intermediate commits may add tests/contracts but cannot silently enable guest execution. Before each task inspect `git status --short` and the staged diff, preserving unrelated work. Commit task-owned changes only when implementation/commits have been authorized; suggested messages below are checkpoints, not instructions to commit during planning.

const (
    SpaceDeny SpaceDecision = "deny"
    SpaceAllow SpaceDecision = "allow"
